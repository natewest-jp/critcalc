# Translation setup — 2026-11-19

Round 2 of the translation item in `docs/todo.md`: the platform the frame pilot runs on.
Two stacked branches, `feat/i18n-wiring` (Paraglide, locale routing, search) and
`feat/i18n-pilot-prep` (the first extracted surface, the ledger bridge, message checks,
CJK type). English renders exactly as before; nothing is translated yet.

## What was built

- **Paraglide 3.2.2**, pinned exactly, with `@inlang/plugin-message-format` 4.5.0 loaded
  from `node_modules` instead of a CDN, so a build makes no network fetch. The npm
  maintainer changed between 2.x and 3.x. The GitHub repo was transferred by its owner
  (`opral/paraglide-js` now redirects to `generaltranslation/paraglide-js`), and Svelte's
  own `sv add paraglide` installs `^3.2.2`, so 3.x is the sanctioned line.
- **Where things live.** `messages/{en,ja,zh}.json` hold the text. `project.inlang/` holds
  the project (`settings.json`) and the compiler options (`paraglide.config.js`, read by
  both the Vite plugin and the `i18n` script that `check` runs). The compiled output in
  `src/lib/paraglide/` is gitignored. `src/lib/i18n/` holds the site's side: `locale.ts`
  (`<html lang>`, `og:locale`, which locales are indexed) and `paths.ts`.
- **The locale is in the path.** English is unprefixed; `/ja/…` and `/zh/…` for the others.
  The strategy is `url` then `baseLocale` only: no cookie and no browser-language guess, so
  a shared link renders in the language of its path for every reader, and `?r=` never
  carries a locale. `reroute` (`src/hooks.ts`) maps `/ja/planner` onto the `/planner`
  route; the server hook (`src/hooks.server.ts`) scopes each prerendered page's locale and
  fills `<html lang>`. Chinese is `zh` in the path and `zh-Hans` in `lang`, so browsers
  pick Simplified glyphs.
- **Every internal URL goes through `$lib/i18n/paths`.** `hrefTo('/planner')` out,
  `routeOf(page.url)` in. `page.url` keeps the prefix (reroute changes which route renders,
  not the URL), so a bare comparison against `'/planner'` fails on every locale but
  English. Converting the sites fixed real breakage on `/ja/`: the tools layout's tool
  lookup, the Visualizers `?i=` import and the coverage door all compared a raw pathname.
  Route tables (menu sections, help chapters) are now canonical and localized where they
  are read, because a module-level table of links would freeze one locale for the whole
  prerender. `svelte/no-navigation-without-resolve` is off; `conventions.test.ts` holds a
  stricter rule in its place.
- **Search.** Every page in a hidden locale says `noindex` in its head, and `static/_headers`
  says it again for `/ja`, `/ja/*`, `/zh` and `/zh/*`. The sitemap is unchanged. The hidden
  pages prerender from an entry list in `svelte.config.js`, built from the route tree and
  the inlang project, since nothing links to them. `isIndexed` in `locale.ts` is the switch.
- **The first surface: the error page** (`+error.svelte`, ten messages under the ledger's own
  `errors_*` keys). It proves the chain end to end: extraction, the ledger, the build, the
  404 fallback.
- **The ledger bridge.** `scripts/extract-strings.mjs` reads `messages/en.json` back: each
  key is a message on the surface its key names, located at its `m.<key>(` call sites. A
  literal elsewhere that mints the same key joins it (RenderCrash's "Report this" still
  does); one with different text is reported as a conflict, and an en.json key nothing
  calls is reported as unused. The ledger counted 2,695 messages and the same 20 `errors`
  keys before and after the error page moved.
- **Message checks** (`src/lib/i18n/messages.test.ts`): every English message compiles and
  renders its own text, every locale has a file, and a translation uses only English keys
  with the same placeholders.
- **CJK type** (`app.css`, end of file). Under `:lang(ja)` and `:lang(zh-Hans)` every font
  stack names the platform's own CJK sans before the generic family: Hiragino or PingFang
  on Apple, Yu Gothic or YaHei on Windows, Noto elsewhere. The knob is `--font-cjk`, one
  list per locale. Without it, Bitter's `serif` would set CJK headings in a Mincho or Song
  serif. Headings in gothic is a first cut for Nate to judge.

## Traps found on the way

- ⚠️ `paraglide-js compile` reports success when the plugin fails to load, and compiles no
  messages. The first message check is what notices; it was seen failing with a broken
  plugin path.
- ⚠️ Plugin and message paths in `settings.json` resolve from the repo root, not from
  `project.inlang/`.
- ⚠️ SvelteKit's `resolve()` returns a relative path (`./help`) while prerendering, and
  `localizeHref` makes anything not starting with `/` absolute. The first build shipped
  `http://sveltekit-prerender/help` links on English pages too, found by grepping `build/`.
  `hrefTo` localizes the root path directly; the reason is at its declaration.
- The middleware's de-localized request is not passed on: `reroute` already strips the
  prefix, and stripping it twice is the loop Paraglide's notes warn about.
- The 404 fallback is one English shell for every unknown path. The root layout sets
  `<html lang>` on mount, so a `/ja/` typo gets the CJK rules.
- `trailingSlash: 'never'` in the Paraglide config matches SvelteKit's default, so the
  Japanese landing is `/ja`, never `/ja/`.

## Verified

Gates on both branches: vitest (2,972), check, lint, build. `npm run test:e2e:chrome` was
green on the wiring branch (73 passed). Against the production build in headless Chrome:
`<html lang>`, robots and `og:url` on every locale; links on `/ja` stay in `/ja`; tool
doors, the wordmark and the landing doors; `?r=` and `?i=` imports; menu sections pushed,
Back, Escape, and closing a section reloaded on its own route; a `/ja/` typo renders the
Japanese error page (with one throwaway string, not committed) under the CJK stack while
the English 404 is unchanged. Nothing here has been looked at in real Safari.

  the sitemap, `_headers`, `isIndexed`, and a language switcher, which links with
  `data-sveltekit-reload` because the locale is fixed for the life of a document.

  Check it when a tool interior is translated.

## Plex CJK, weighed after the round (for the decision after the pilot)

Nate asked whether IBM Plex's CJK cuts would guarantee layout better than system fonts.
Measured 2026-11-19:

- **Plex Sans JP** (`@fontsource/ibm-plex-sans-jp` 5.3.1): seven static weights, no
  variable cut. Each weight is about 2.5 MB in 124 `unicode-range` slices, so a page
  fetches only the slices its characters need; a page of frame text is likely a few
  hundred KB on a first visit, then cached.
- **Plex Sans SC/TC** (`@ibm/plex-sans-sc` 1.1.0, `@ibm/plex-sans-tc` 1.1.1, IBM's own
  packages; not on fontsource): about 3.8 MB per weight complete, with split builds in
  the package. They would be self-hosted under `/assets` (add-only).
- **What it would and would not fix:** CJK glyphs are near-uniform em squares in every
  font, so line length barely moves between Hiragino, Yu Gothic, PingFang and Noto. What
  varies is vertical metrics, how CJK sits beside Latin, and quality (Windows' Yu Gothic
  is the weak one). Plex fixes those and matches Plex Latin by design. It does not fix
  line breaking or string length, which are the likelier breaks and are what the
  pseudo-locale finds. Costs: the download, a reduced weight ladder (static weights), and
  a font swap on first visit, which is itself a layout shift.
- **Claude's recommendation:** system fonts for the pilot, then decide by eye from a `/lab`
  side-by-side. Both choices sit behind `--font-cjk`, so switching is cheap.
